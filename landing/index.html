// WHY

为什么普通方法删不掉？

问题根源在于 Windows 系统的路径解析阶段，而非文件系统损坏。深入理解底层差异，安全清理更放心。

✕ Win32 子系统劫持（资源管理器 / del / rm / 常见工具）

  • 历史包袱：DOS 1.0 时代为了将 NUL、CON、PRN 用作流重定向，将保留名硬编码进系统。
  • 路径解析劫持：Win32 API（kernel32.dll / CreateFileW）在解析路径时，一律将其重定向至 \Device\Null 等字符设备。
  • 死锁假象：普通删除命令以为自己在删设备，根本无法触及 NTFS 磁盘底层那个字面名叫 NUL 的物理文件。

✓ delete-nul（直达 NT 原生对象管理器）

  • NT 原生路径直通：给路径注入 \\?\（Unicode NT 扩展前缀），告知操作系统直接跳过 Win32 规范化过滤。
  • 精准文件枚举：通过底层原生 API 枚举真实物理磁盘项，精准定位受困文件。
  • 物理定点清除与复核：直达 NT 对象管理器执行精准物理抹除，并再次递归复核确认残留数为 0。

同一串字符，两种解析

WIN32del NUL命中 DOS 设备对象，磁盘上的文件纹丝不动
NTdel \\?\C:\work\NUL跳过规范化，按字面路径精确命中

规范流程：底层枚举 → 精确匹配裸保留名 → 锁定物理路径 → 注入 \\?\ 前缀精准清除 → 自动复核残留。先只读预检，经确认才删除。

// FAQ

常见问题解答

针对真实开发与日常系统维护中的高频疑问，提供清晰权威的解答。

Git 克隆/检出报错 "unable to create file ...: Invalid argument" 怎么办？

这是因为跨平台拉取了由 Linux / macOS 开发者提交的包含 nul、aux 等文件的仓库。Windows 资源管理器与普通 Git 无法创建或删除它们。只需用 delete-nul 扫描当前仓库路径，先只读预检，再确认清除该异常文件，随后 git status 即可恢复正常。

为什么不用第三方“强力粉碎机”或重启进入 WinPE？

绝大多数第三方粉碎工具同样基于 Win32 API 查找文件，面对保留名依然会死循环或提示“找不到指定文件”；而进入 WinPE 操作门槛高、容易误操作且无法自动化。delete-nul 原生几行轻量脚本直接调用 NT 原生路径，零成本、免安装、秒级解决。

杀毒软件报毒或 PowerShell 策略拦截怎么处理？

本项目 100% 开源纯透明，不含任何可执行二进制文件、无混淆、无 Base64 加密。bat 只是调用系统自带 PowerShell 的薄包装。若受组织组策略拦截，可直接切换到 Hero 区域的【纯文本】Tab，使用系统纯原生 CMD 管道命令运行，无需加载 PowerShell。

提示 FAILED 或文件正被占用无法删除？

通常是因为资源管理器的“预览窗格”、VSCode、终端或其它后台程序正打开着该目录。只需关闭相关程序后重试；若涉及系统特权路径（如 Program Files），运行时加上 -Elevate 参数以管理员身份执行提权。

删除后能恢复吗？会进回收站吗？

不能恢复，也不会进回收站。因为 Windows 回收站本身依赖 Win32 子系统，无法接收保留名文件。因此 delete-nul 严格贯彻「先列后删」安全策略，先只读罗列所有待删文件，经人工确认（Y）后才执行物理移除。

会误伤 nul.txt 或正常业务文件吗？

默认绝不误伤！匹配引擎采用强正则 \\nul$ 进行裸名全字匹配，nul.txt、con.png 等带扩展名的正常文件会被系统完全豁免保护。如需显式连同扩展名一起处理，才需手动加上 -IncludeExtension 参数。
